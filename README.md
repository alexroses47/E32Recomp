# E32Recomp — static recompilation for Symbian games

**Research project by alexroses47.** E32Recomp aims to make **native ports of Symbian games** (S60v3, S60v5,
N-Gage 2.0) to other platforms possible: read the original executable, translate its code, and reimplement
only the parts of Symbian OS that games actually use.

## What is E32Recomp?

- **E32** is the executable format of Symbian OS: every Symbian program (`.exe`, `.dll`, `.app`) is an
  *E32 image* — ARM code, relocations and a table of imports from the system libraries.
- **Recomp** stands for **static recompilation**, the technique behind N64Recomp and XenonRecomp: instead of
  emulating the CPU while the game runs, the game's machine code is translated once, ahead of time, into C,
  and compiled natively for the target (Nintendo 3DS, PC, Switch…).
- So **E32Recomp = a toolchain that turns the E32 executables of a Symbian game into native code**, plus a
  **runtime** that reimplements the Symbian functions the game calls (memory, files, graphics, touch, sound),
  so the result runs without Symbian and without an emulator.

Each user runs it on their own copy of a game; the generated code is never distributed.

> ⚠️ **Experimental. Early stage.** Today E32Recomp is a set of tools and a small runtime that can execute
> functions of a Symbian executable; it cannot run a whole game yet. It contains **no games and no game
> code**: every user works with their own copy. Not affiliated with Nokia, Symbian or any game publisher.

## Why

Emulators like EKA2L1 reproduce the whole phone. That is great for preservation, but too heavy for small
devices such as the Nintendo 3DS. Static recompilation projects (N64Recomp, XenonRecomp) showed another way:
translate the game's code once into C, link it with a small runtime, and build a native program. For Symbian
the CPU part (ARM → C) is approachable; the hard part is the OS layer. E32Recomp bets on **reimplementing only
the subset of Symbian that games use**, verified function by function against the original.

## What exists today

| Part | Status |
|---|---|
| `.sis` installer extractor (`e32recomp/sis_extract.py`) | Works (SIS 9.x, S60v3/v5) |
| E32 image unpacker with BytePair decompression (`e32recomp/e32_unpack.py`) | Works |
| Import resolver: ordinals → names with the Symbian `.def` tables (`e32recomp/make_import_map.py`) | Works |
| C++ RTTI / vtable scanner and class map (`e32recomp/rtti_scan.py`, `e32recomp/classes_doc.py`) | Works |
| Ghidra scripts for E32 images (`e32recomp/ghidra/`) | Works |
| **Runtime, stage 0** (`e32recomp/e32emu.py`): loads an E32 image with relocations in Unicorn, replaces imports with HLE implementations and calls original functions | Works for pure logic (math, physics); no OS services yet |
| Inventory of a game's own functions by stage: discovered / studied / reimplemented / verified (`e32recomp/game_functions.py`) | Works |
| Progress page with function grids, like AnyPS5 (`tools/progress.py`) | Works |

All of this was built for, and is used every day by, the first reference game:
**[Bounce Touch 3D](https://github.com/alexroses47/Bounce-Touch-3D)**, a native Nintendo 3DS port of
Bounce Touch (S60v5), where it powers the differential tests that compare the port with the original.

## Roadmap

1. **HLE of the core OS** (`euser`: heap, descriptors, `User::`, active objects, timers) so that whole
   subsystems of a game can run.
2. **Static recompiler (ARM/Thumb → C)** for game logic, starting *hybrid*: recompile the original physics
   and scripts of Bounce Touch, keep the port's own renderer, and check with the comparator that both give the
   same numbers.
3. **Platform layer** for one game: window server and bitmaps (`ws32`, `fbscli`, `bitgdi`), touch and keys
   (`cone`, `eikcore`, `avkon`), audio (`mediaclientaudiostream`).
4. **A second game** (another KA3D or N-Gage 2.0 title) to prove that the runtime generalises.

## Quick start

Python 3.10+; the runtime needs [Unicorn](https://www.unicorn-engine.org/) (`pip install unicorn`).

```sh
python3 e32recomp/sis_extract.py "Your Game.sis" work/extracted          # extract your own copy
python3 e32recomp/e32_unpack.py work/extracted/sys/bin/Game.exe work/Game_unpacked.exe
python3 e32recomp/make_import_map.py work/Game_unpacked.exe third_party/symbian-defs work/
python3 tools/progress.py                                               # progress page in docs/
```

To track a new game, add `games/<name>.tsv` (`kind  dll  ordinal  symbol`, from `make_import_map.py`) and,
optionally, `games/<name>_functions.tsv` (from `e32recomp/game_functions.py`: addresses, names and stages, no code).

## Español

**Proyecto de investigación de alexroses47.** E32Recomp busca hacer posibles **ports nativos de juegos de
Symbian** (S60v3, S60v5, N-Gage 2.0) a otras plataformas: leer el ejecutable original, traducir su código y
reimplementar solo la parte de Symbian OS que los juegos usan de verdad.

**¿Qué es E32Recomp?**

- **E32** es el formato de los ejecutables de Symbian OS: todo programa de Symbian (`.exe`, `.dll`, `.app`) es
  una *imagen E32*, con código ARM, relocaciones y una tabla de importaciones de las bibliotecas del sistema.
- **Recomp** viene de **recompilación estática**, la técnica de N64Recomp y XenonRecomp: en lugar de emular el
  procesador mientras el juego corre, su código máquina se traduce una sola vez, por adelantado, a C, y se
  compila de forma nativa para el destino (Nintendo 3DS, PC, Switch…).
- Es decir, **E32Recomp = herramientas que convierten los ejecutables E32 de un juego de Symbian en código
  nativo**, más un **runtime** que reimplementa las funciones de Symbian que el juego llama (memoria, archivos,
  gráficos, táctil, sonido), para que el resultado funcione sin Symbian y sin emulador.

Cada persona lo usa con su propia copia del juego; el código generado nunca se distribuye.

> ⚠️ **Experimental, en fase temprana.** Hoy E32Recomp es un conjunto de herramientas y un runtime pequeño
> que ejecuta funciones de un ejecutable de Symbian; todavía no puede ejecutar un juego entero. **No contiene
> juegos ni código de juegos**: cada persona trabaja con su propia copia. Sin relación con Nokia, Symbian ni
> ninguna editora.

- **Progreso:** [alexroses47.github.io/E32Recomp](https://alexroses47.github.io/E32Recomp/): cuántas de las
  funciones de Symbian que importan los juegos de referencia implementa el runtime, biblioteca por biblioteca.
- **Por qué:** emuladores como EKA2L1 reproducen el teléfono entero; es ideal para preservar, pero pesa
  demasiado para consolas pequeñas como la 3DS. La recompilación estática (N64Recomp, XenonRecomp) traduce el
  código del juego a C una vez y lo enlaza con un runtime pequeño. En Symbian la parte de CPU es asumible; lo
  difícil es el sistema operativo, y E32Recomp apuesta por **reimplementar solo lo que usan los juegos**,
  verificado función a función contra el original.
- **Qué hay hoy:** extractor de `.sis`, desempaquetador E32 (BytePair), resolución de importaciones con las
  tablas `.def` de Symbian, escáner de RTTI y mapa de clases, scripts de Ghidra y el **runtime en etapa 0**
  (Unicorn + relocaciones + implementaciones HLE de importaciones), que ya ejecuta la lógica pura del juego.
- **Juego de referencia:** [Bounce Touch 3D](https://github.com/alexroses47/Bounce-Touch-3D), port nativo para
  3DS de Bounce Touch, donde estas herramientas comparan el port con el original en cada cambio.
- **Hoja de ruta:** 1) HLE del núcleo (`euser`); 2) recompilador estático ARM/Thumb → C, empezando por un
  híbrido con la física y los guiones de Bounce Touch; 3) capa de plataforma (gráficos, táctil, audio) para un
  juego; 4) un segundo juego para demostrar que se generaliza.
- **Legal:** solo código propio y las tablas de exportaciones de Symbian (EPL-1.0). No contiene, descarga ni
  distribuye juegos; lo que se genere a partir de un juego se queda en el equipo de cada uno.
